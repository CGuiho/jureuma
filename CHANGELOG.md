# Changelog

All notable changes to jureuma are recorded here. Versions are planned and applied with GUIHO Mirror (`mirror.yaml`); entries are written at release time.

## Unreleased

### Added

- `jureuma init` also protects OpenCode sessions in the project: with the agent-tool deny rules it appends read-deny rules for `*.unencrypted.json`, `*.unencrypted.jsonc` and `$HOME/.guiho/jureuma/*` to the project's `opencode.json` (or `opencode.jsonc`), OpenCode V2's ordered `permissions` array (last matching rule wins), creating the file with its `$schema` when absent. `--agent-deny-rules` governs both tools, `check` reports both, and `agent instruction remove` / `uninstall` remove exactly what jureuma recorded for each tool.
- `.jsonc` is now fully two-way for the human-owned files: a comment-preserving writer updates an existing `.jsonc` plaintext or schema in place from `set`, `unset`, `decrypt` and `schema infer` (`WritePlain` and the schema write). Only the minimal byte spans a change needs are spliced; comments, blank lines, formatting, number text (`1e3`, `-0`) and string-escape spelling outside them survive byte for byte, existing trailing commas are preserved (and reused as separators) and no new trailing comma is emitted. A change that cannot be represented — or a file that no longer parses — is refused with nothing written. `init` also creates a missing `.jsonc` plaintext side. `.json` stays the default and the encrypted file stays `.json`.
- The two single-file states are first class. With only the unencrypted file present, `set` and `unset` build (or refresh) the encrypted sibling from that document under the pair key its `$jureuma` header records — no private key required — while `encrypt` rebuilds it the same way when no saved copy or git `HEAD` version exists. The mirror rule is unchanged: an unsaved human edit (or a value jureuma cannot prove unchanged) is never replaced, and the path stays pending.
- `jureuma init` repairs pair files and chooses keys. Old jureuma state (a `$jureuma` block with `format: 1`, or a headerless plaintext) is repaired in place into the format-2 identity header plus the `$schema` pointer — keylessly, keeping every value, `sync` and `pending`, and byte-idempotent on an already-repaired pair; a block jureuma cannot parse is reported, never overwritten. For a pair with no recorded identity, `init` offers the stored keys in a terminal (label and short key ID, plus `create a new key`), or takes `--key-id` / `--key-label`; without a terminal it creates a new key labeled with the repository name.
- The pair's schema travels with its files: `encrypt` and sibling builds embed the schema document encrypted to the pair key (`$jureuma.schema = { path, c }`, re-encrypted under a retired key as needed), `decrypt` restores a missing local schema from it — never clobbering an existing file, warning when it differs — and `key rotate` moves the copy to the new key like every value. `schema infer` declares the optional top-level `$schema` string property in generated schemas and refreshes both the pointer and the copy.
- `status` and `check` report the pair across all four file states (only the unencrypted file, only the encrypted file, both, legacy jureuma state), warn when both files exist (the riskiest state), and report `$schema` pointer presence, path match and drift between the embedded schema copy and the local file — value-free as always.
- `jureuma.yaml` may bind the project's key pair: an optional top-level `key:` names the one key pair every configured pair uses. It is a full key ID (`k_` plus 32 lowercase hex characters; labels stay display metadata and are refused, so the binding is verifiable without the keystore), and an empty or malformed value is a validation error (exit 4) on load. When the binding is set, every pair's recorded `$jureuma.keyId` must match it — a disagreement fails with exit 5 on every command that resolves pairs, never a silent re-encrypt — while a pair with no recorded identity (both files absent, or a headerless plaintext) is not a disagreement. `init` uses the bound key for a pair with no recorded identity (`--key-id` / `--key-label` that contradict the binding are a usage error, a missing key is exit 5 pointing at `jureuma key list`), writes the binding after creating or choosing a key, and `key rotate` updates it to the new key ID (an absent binding stays absent, and a binding that cannot be updated fails the command after the rotation is reported). Both write exactly one spliced top-level line — every comment, blank line, ordering and quoting elsewhere stays byte-identical — and an existing binding is never overwritten.

### Changed

- `jureuma run` injects the document into `JUREUMA_CONFIG` by default (with `--format json|file`), the name `auth-ui` already configures: the CLI default, the denylist exception and every documented surface agree on it. `JUREUMA_CONFIG` is the run-env denylist's only exception; `JUREUMA_` and every other `JUREUMA_*` name are refused as `--env-name` / `run.envName`.
- Both pair files carry the pair identity: the unencrypted file gains a `$jureuma` header (`format`, `publicKey`, `keyId`, `home`) and a top-level `$schema` pointer, written by `init` and `decrypt` and preserved byte-identically by every other write. `$jureuma` and `$schema` are reserved metadata: never a value, listing, injection or `set`/`unset` path. Files carrying old jureuma state refuse every mutation with `run jureuma init to repair`; reads keep working. `set` validates against the readable schema and warns explicitly when validation is skipped.
- A configuration document that is present but invalid — a schema violation, or a semantic one such as a duplicate pair name or an empty or malformed `key:` binding — now fails every load as a validation error (exit 4) instead of a general failure. Files that cannot be read or parsed keep failing as general failures.
- `init` converges a project on one key pair: when it creates or chooses a key for a pair with no recorded identity and no other configured pair records a different key, that key is written as the `jureuma.yaml` key binding and the pairs processed after it use it. Previously every fresh pair got its own new key; a project whose pairs already record different keys keeps them (init adds no binding there and says so).

## 0.2.0 - 2026-10-17

### Added

- `inject` is an accepted alias of `run`: the same flags, injected document, redacted child output and exit codes (`jureuma inject -- <command>`).

## 0.1.0 - 2026-10-16

### Added

- The agent-safe configuration CLI: `init`, `encrypt`, `decrypt`, `set`, `unset`, `get`, `run`, `list`, `status`, `check`, `key show|export|rotate|retire`, `schema infer`, `juju-enable`, `juju-disable`, `agent skill|instruction|prompt`, `upgrade check|list` and `uninstall`, with the convention help flags (`--help-docs`, `--help-tree`, `--help-tree-depth`, `--help-tree-global-flags`).
- Configuration pairs plus a schema: the gitignored `<stem>.unencrypted.json` plaintext, the committed `<stem>.encrypted.json` whose every value is X25519-encrypted with readable field names, and a committed JSON or JSONC JSON Schema draft 2020-12 (`schema infer` generates it); dedicated locks keep the pair in sync.
- Agent-safe injection: `jureuma run -- <cmd>` injects the decrypted document (JSON by default; `--format flatten|file`, `--env-name`) into `JUREUMA_CONFIG`, private keys stripped, the document hardened through memfd or a 0600 temp file, and child output redacted.
- The human-only gate: `decrypt`, `get`, `key show --private` and `key export` require a real terminal and a typed confirmation word, refuse agent markers, and audit `--dangerously-bypass-protections`.
- Lifecycle automation: `devops/install.sh`/`install.ps1` and `uninstall.sh`/`uninstall.ps1` with version and channel selection over every catalog page, SHA-256 verification, immutable payloads under `~/.guiho/jureuma/versions/<version>/`, the released stable launcher in `~/.guiho/bin`, transactional rollback, PATH integration and the managed `AGENTS.md` block.
- Upgrades: `jureuma upgrade` runs a synchronous journaled transaction (staging, verification against `checksums.txt` and `artifacts.json`, `--version` and `__self-test` of the candidate, immutable version directory, skill projections, atomic `current.json`, launcher verification, complete rollback) that repairs an interrupted transaction on the next invocation and terminates every verified old-payload process before activation; the stable launcher resolves the active payload and falls back to the retained previous version.
- The release artifact pipeline: six cross-compiled payloads, six launcher binaries, the `guiho-s-jureuma` skill, the three prompts, the instruction source, both configuration schemas, example configurations, `artifacts.json` and `checksums.txt`.

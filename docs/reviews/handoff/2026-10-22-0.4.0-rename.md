# Human Review — ZeZé 0.4.0 (2026-10-22)

## What Shipped

The project moved to the ZeZé identity in **one breaking release**, on CG's
instruction to rename every occurrence and then commit, push and release, with
backward compatibility explicitly waived.

- **Identity.** The repository, the module, the CLI binary, the stable
  launcher, the CLI home, the project and global configuration files, the
  structured error-tag prefix, the managed-block markers and the shipped agent
  artifacts all now speak `zeze` / ZeZé. Prose and titles read **ZeZé**;
  machine identifiers and file names are ASCII `zeze`.
- **CLI surface.** `zeze`, `zeze-launcher-<os>-<arch>`, `ZEZE_*`
  environment variables (including `ZEZE_CONFIG`, `ZEZE_USER_HOME`,
  `ZEZE_PRIVATE_KEY`), `[ZEZE:<KIND>]` error tags, `~/.guiho/zeze/` home,
  `zeze.yaml` / `zeze.global.yaml`, `guiho-s-zeze` skill and the three
  `guiho-p-zeze*` prompts.
- **Zero backward compatibility.** No alias, shim, fallback or deprecation
  window. The obsolete alias command surface was removed. Nothing recognises
  the former names; the only record of them is the single named exemption
  [docs/2026-10-22-zeze-migration-instruction.md](../../2026-10-22-zeze-migration-instruction.md).
- **Configuration pairs are untouched.** `config.unencrypted.json`,
  `config.encrypted.json` and `config.schema.json` (+ `.jsonc`) keep their
  names and contents; key IDs, public keys and the `key:` binding are data and
  never renamed.
- **Version pinning.** `devops/version-sync.sh` pins the
  `yaml-language-server` schema URLs in both example configs and the
  `version`/`metadata.version` frontmatter of the seven shipped agent
  artifacts to `v0.4.0`.

## What You Should Test

Use a throw-away home and a scratch git project — **never** the real
`~/.guiho/zeze/`:

```sh
export ZEZE_USER_HOME=/tmp/opencode/review-home
export ZEZE_NO_UPDATE_CHECK=1
mkdir -p "$ZEZE_USER_HOME" /tmp/opencode/review-proj
cd /tmp/opencode/review-proj && git init -q
BIN=/root/swe/zeze/bin/zeze      # ZEZE_VERSION=0.4.0 sh devops/build.sh
# (a plain rebuild after the release commits reports 0.0.0-dev by design:
#  devops/version.sh only reads a v<semver> tag at HEAD)
```

1. **Version and identity**
   ```sh
   "$BIN" --version                # 0.4.0, nothing else
   "$BIN" --help                   # command tree, ZeZé in the prose
   "$BIN" inject -- true           # must fail: the alias surface is gone
   ```
2. **Fresh pair**
   ```sh
   "$BIN" init --agent-deny-rules no
   "$BIN" set /greeting --json '"hi"'
   "$BIN" run -- sh -c 'printf %s "$ZEZE_CONFIG"'   # redacted document
   "$BIN" check                                     # 0 failures
   ```
3. **Old environment names are ignored**
   ```sh
   ZEZE_CONFIG= "$BIN" run --env-name ZEZE_ -- true  # refused, exit 125 [ZEZE:USAGE]
   ```
4. **Managed blocks.** In the scratch project, `cat AGENTS.md .gitignore` —
   the markers read `zeze managed block`, and no second block appears on a
   second `init`.
5. **Install.** Reinstall from the new release with its own installer
   (`curl -fsSL https://raw.githubusercontent.com/CGuiho/zeze/main/devops/install.sh | sh`)
   in a throw-away `HOME`, then `zeze --version` → `0.4.0` and
   `zeze key list` → no private material.
6. **Human-only flows** (`decrypt`, `get`, `key show --private`,
   `key export`) need a real terminal and the typed confirmation word — test
   them from your terminal, not from an agent session.
7. **Real migration.** Only on a machine that still has the old installation,
   and only after reading
   [docs/2026-10-22-zeze-migration-instruction.md](../../2026-10-22-zeze-migration-instruction.md):
   back up and carry the private keys first.

Full battery: `runx run ci-check` and `runx run test-e2e`.

## Known Limitations

- **`shellcheck` is not installed on this host**, so `shell-lint` syntax-checked
  every `devops/*.sh` with `sh -n`, `dash -n` and `bash -n` but skipped the
  linter pass.
- **`pwsh` is not installed on this host**, so the PowerShell parser never
  validated `devops/install.ps1` / `uninstall.ps1`, and the **Windows
  installers are unexercised**: the Windows payloads and launchers are built
  and checksummed but no Windows runtime was executed.
- `runx run test-installers` was **not** run in this release train; the Linux
  installer path is covered by the smoke test and by the shipped prompts, not
  by a full local release-catalog run.
- The four historical releases and their tags are intentionally untouched:
  their titles and asset names still carry the former identity. That is
  recorded, not a defect to fix.
- Configuration pairs created before the rename keep working untouched. A pair
  flagged with a legacy or malformed identity header is repaired with
  `zeze init`, never by hand.

## Migration Pointer

[docs/2026-10-22-zeze-migration-instruction.md](../../2026-10-22-zeze-migration-instruction.md)
is the **single named exemption** where the former names survive, and the one
ordered procedure for migrating a machine: back up and export the private
keys, move the whole CLI home, verify key availability, replace the launcher
and installation, rename the configuration files, replace the managed blocks,
re-establish the deny rules, rename the environment variables, rename the agent
artifacts, then verify. The private keys are the only unrecoverable item —
without them every `*.encrypted.json` in every project becomes permanently
undecryptable.
